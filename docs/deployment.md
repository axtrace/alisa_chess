# Поставка функций через GitHub Actions

Каждая новая версия функции, в том числе откат, проходит через Actions репозитория `axtrace/alisa_chess`. В истории запуска видны исходный коммит, контрольная сумма ZIP и активный ID версии в Yandex Cloud. Этот порядок начинает действовать после попадания workflows и поставляемого кода в основную ветку.

| Событие | Результат |
| --- | --- |
| Pull request в `master` или `main` | CI проверяет код и собирает три варианта ZIP без облачных секретов |
| Push в основную ветку (`master` или `main`) | Deploy testing functions проверяет коммит и обновляет `alice-chess-testing` |
| Run workflow → Deploy testing functions | Из основной ветки можно повторить поставку навыка или выбрать `api-testing` для API |
| Run workflow → Deploy production skill | Ручная поставка текущего коммита основной ветки в `alice-chess-stable` |

## Что получает каждая функция

| Цель | Обработчик | Память / таймаут | Движок | Настройки |
| --- | --- | --- | --- | --- |
| `testing` | `shared_alice_serverless.handler` | 2 ГиБ / 5 с | Stockfish 19 | Тестовый навык «Голосовые шахматы», YDB, закрытый IAM-вызов, текущий разрешённый тестер, тег `shared-pilot` |
| `api-testing` | `app_serverless.handler` | 1 ГиБ / 30 с | Stockfish 19 | Тестовая YDB и сервисный аккаунт API, тег Gateway `api-testing` |
| `production` | `alice_serverless.handler` | 8 ГиБ / 5 с | Stockfish 14.1 | Состояние Диалогов, `requirements.txt`, без сервисного аккаунта исполнения |

Все три цели используют рантайм `python314`. Перед записью workflow сверяет текущую версию с ожидаемыми параметрами. При расхождении проверьте целевой ID и согласуйте конфигурацию в PR. Псевдоним тестера берётся из действующей закрытой тестовой функции.

## Как проверить поставку

1. [CI](../.github/workflows/ci.yml) запускает Ruff и pytest. В отдельном задании на Ubuntu 22.04 он проверяет SHA-256 скачанного движка, собирает ZIP по списку модулей, распаковывает его, устанавливает зависимости в чистое окружение Python 3.14, импортирует обработчик и делает реальный ход Stockfish.
2. [Общий workflow поставки](../.github/workflows/release-function.yml) получает проверенный ZIP из того же запуска, сверяет хеш и актуальность коммита. Версии одной функции публикуются последовательно.
3. Задание `publish` загружает ZIP в закрытый бакет по ключу `github-actions/<цель>/<git SHA>/<SHA-256 ZIP>.zip` и создаёт версию по её точному ID функции. После создания оно читает `$latest` и именованный тег, сверяет конфигурацию и пишет результат в **Summary** запуска. В описании облачной версии записаны номер запуска, коммит и хеш ZIP.
4. Для отката верните нужное изменение через PR. После слияния тестовый навык обновится автоматически. Прод и API обновляются соответствующим ручным workflow.

## Доступ

Используются существующие секреты Actions `YC_SA_JSON_CREDENTIALS_2`, `FOLDER_ID_2` и `BUCKET_NAME_2`. Ключ нужен только шагу публикации на одноразовом hosted runner. У аккаунта поставки должны быть права читать и создавать версии трёх функций, писать и читать объекты в бакете и использовать сервисный аккаунт исполнения тестовых функций. При пользовательском ACL загрузчик сохраняет полный доступ к объекту, а сервисный аккаунт исполнения тестовой функции получает чтение.

Workflow задаёт канал поставки в репозитории. Возможность создавать версии из консоли или личного CLI определяет IAM каталога, включая унаследованные роли. Для технического запрета прямых поставок право создания версий должно оставаться у аккаунта GitHub Actions. Пересмотр прав владельцев и администраторов выполняется отдельно.
