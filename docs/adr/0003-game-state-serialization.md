# ADR-0003: Сериализация GameState (Pydantic + версионирование + миграции)

- **Статус:** Accepted
- **Дата:** 2025-11-01
- **Авторы:** alisa_chess team

## Контекст

Состояние партии живёт только между запросами через `state.user.game_state` — JSON-объект, который платформа Алисы возвращает навыку. У этого канала есть жёсткие ограничения:

- **Размер ограничен** (~1 KB безопасно для `user_state_update`).
- **Структура неизвестна заранее.** Пользователь может прийти со старым state, сохранённым ещё до текущей версии деплоя.
- **Любая ошибка десериализации губит партию.** Если кинуть исключение при разборе — пользователь потеряет ход.

Изначально state был словарём с произвольными ключами, без явной схемы и версии. Любое добавление поля ломало совместимость со «старыми» сессиями.

## Решение

1. **Pydantic v2 как единственный источник истины.** Схемы [`GameStateV1`](../../game_state.py) и [`GameStateV2`](../../game_state.py) — `BaseModel` с `@field_validator` для проверки FEN, цветов, enum-состояний.
2. **Явное версионирование через поле `_version`.**
   - V1: поля без `_version` (legacy).
   - V2: `_version = 2`, расширенная структура (`current_turn`, `needs_promotion`, …).
3. **Автоматическая миграция при чтении.** [`GameState.from_dict`](../../game_state.py) определяет версию по наличию `_version` и пути ключей, парсит как `GameStateV1`/`GameStateV2`, при необходимости вызывает `_migrate_v1_to_v2`. Запись всегда выполняется в формате V2 — это естественно «вытягивает» legacy-сессии при первом обновлении.
4. **Graceful fallback.** [`restore_game_from_state`](../../game_state.py) оборачивает каждый шаг восстановления (FEN-доска, enum-парсинг, side-fields) в try/except. Если конкретное поле битое — оно сбрасывается в default, а партия восстанавливается на максимально возможном уровне, вместо «всё или ничего».
5. **`SkillState(str, Enum)`** наследует от `str`, чтобы JSON-сериализация автоматически давала строку, и V1-state со строковым `skill_state` остался валидным.
6. **Идемпотентность по `message_id`** живёт отдельно — в `session_state.last_message_id`, не внутри `game_state`. Это отдельный контракт; см. [`alice_chess.py`](../../alice_chess.py).

## Последствия

**Плюсы:**
- Любое поле теперь имеет документированный валидатор; нельзя случайно положить в state мусор.
- Старые партии не теряются при выкатке новой версии: V1 продолжает читаться и переписывается в V2 на ходу.
- Любая ошибка валидации видна в логах как сообщение конкретного валидатора, а не «KeyError» в случайном месте.
- Тесты сериализации не зависят от реального Stockfish.

**Минусы и компромиссы:**
- Pydantic — runtime-зависимость. Это добавляет ~3 MB в deployment-bundle и небольшой cold-start penalty. Признан приемлемым: альтернатива (ручные валидаторы) приводит к десяткам строк boilerplate в каждом хендлере.
- Версионирование требует дисциплины: при появлении V3 нужно держать как минимум `_migrate_v2_to_v3` и обновить `from_dict`.
- Поле `_version` начинается с `_` — это нарушает соглашение «private» в Python, но это сознательно: подчёркивает, что поле — служебное и не должно использоваться кодом приложения напрямую.

## Правила эволюции схемы

1. **Новые поля — только опциональные** с разумным default. Иначе старые сессии перестанут парситься.
2. **Удаление поля** — только после полной миграции через целевую V(N+1) и хотя бы одного релиза, в котором новая версия пишется, а старая читается.
3. **Каждая новая мажорная версия = новый класс `GameStateVN`** + миграция `_migrate_v(N-1)_to_vN` + ветка в `from_dict`. Старые версии остаются на чтение неограниченно долго.
4. **Размер state** — следить, чтобы итоговый JSON оставался компактным (< 1 KB на типовой партии). FEN — основной «толстый» компонент, всё остальное должно быть скалярами.
